# Redesign v5 — исследование и проект (24.10.2026)

Статус: фазы A–B (исследование и проектирование). Реализации нет. Ветка `redesign/v5`, резервная точка — тег `backup-v4.7.1`.

## 1. Что подтверждено в живом Bitrix24

| Вопрос | Ответ | Как проверено |
|---|---|---|
| Откуда скрипт берёт брони сейчас | Из DOM календаря в iframe (`.deal-item-contaner`), текст карточек парсится (`parseCard`), в основное окно передаётся через postMessage | Код, живая страница |
| Почему «оборудование на завтра» требует копирования | Календарь показывает один день. Для «не разбирать на завтра» нужен список завтрашнего дня, и его вставляют текстом, скопированным на вкладке «Завтра» | Код `setupDayTools`, `parseDayList` |
| Есть ли данные завтрашнего дня без календаря | **Да.** `BX.rest.callMethod` в основном окне работает по сессии пользователя | Вызовы `crm.deal.fields`, `crm.deal.list`, `crm.deal.productrows.get`, `callBatch` в живом Bitrix24 (только чтение) |
| Поля брони в сделке | `UF_CRM_DATETIME_START` / `UF_CRM_DATETIME_END` (datetime с поясом +03:00), `STAGE_ID`, `STAGE_SEMANTIC_ID` (P в работе, S успех, F отмена), `UF_CRM_1726582733243` (филиал, 111/113), `UF_CRM_ORDER_PLACE_LIST` (id помещения) | `crm.deal.fields` и выборка |
| Откуда оборудование | Товарные строки сделки. Их названия распознаются существующим `findEquipment` (проверено: `Profoto Zoom 2`, «Фон холщовый короткий Тёмный») | `productrows.get` на сделках завтра и сегодня |
| Совпадает ли с календарём | Сегодня для Павелецкой: 13 броней, 28 часов, 1 605 ₽ на 2 админов, как на панели | `computePayout` на данных REST против панели в живом Bitrix |
| Размер данных | День ≈ 80 сделок: 2 запроса списка по 50 + 2 batch по 50 строк | Измерено |
| Отмены | Стадии `LOSE`, `APOLOGY` (семантика F): сегодня 11 из 80, завтра 8 из 80 | Выборка |
| Через полночь | Среди сделок вчера, сегодня и завтра броней, пересекающих полночь, нет, остатков с предыдущего дня нет | Выборка (на этих трёх днях; общего правила нет) |
| Брони с несколькими залами | В выборке нет. Дубли строк внутри сделки бывают (сегодня 1 случай: парковка дважды) | Выборка |

Не проверено: права других сотрудников (у них REST по их сессии может быть ограничен), поведение при тысячах сделок в день, лимиты частоты запросов Bitrix, точность поля `UF_CRM_DATETIME_START` для правок «на лету» (когда админ двигает карточку, меняется ли оно сразу).

## 2. Карта функций (кратко)

Сохранить без изменения: `computePayout` (все ставки, бонус часов, 10% от оборудования, кофе, ставка), `validateCollectorPayload`, `findEquipment`/`quantity`, правило «в одном зале оборудование переезжает: берём максимум, а не сумму», звёздочка и «(утром N)» у первой брони зала (`buildDayList`).
Улучшить: «Скопировать оборудование за день» (брать из REST и показывать таблицей), «Не разбирать на завтра» (брать завтра автоматически), проверка итога (раскрытие состава).
Объединить: «Обзор» и «Выплаты» (сумма и параметры на одном экране), дублирующие кнопки копирования.
Можно убрать: кнопку «Диагностика» с главного экрана (в «Настройки → Для разработчика»), текстовое окно вставки списка (оставить как запасной путь при ошибке REST).
Добавить: переключатель даты, оборудование на завтра автоматически, раскрытие источников, время обновления, статусы загрузки и ошибок, контроль данных (отменённые, дубли, брони без зала).

## 3. Конкуренты: что полезно (оговорка: источники в основном сайты вендоров и каталоги отзывов, независимых разборов мало)

- Rentman (аренда оборудования): проверка доступности по всем проектам и отдельное окно «нехватки» (shortages) при конфликте. Идея для нас: показывать конфликты оборудования между бронями и залами. Ограничение: у нас нет остатков склада в данных, есть только брони.
- Booqable: календарь доступности и «что сегодня выдаётся, что вернуть» одним взглядом. Жалоба пользователей: в календаре не видно всех товаров клиента, ведут таблицу отдельно. Идея: итог по дню плюс раскрытие состава.
- LemonBooking (студии): допы со своим количеством предотвращают двойное бронирование. Идея близка к нашему правилу «одна единица не может быть в двух залах одновременно». Подтвердить с Ильёй.
- Pipedrive: при создании активности рядом виден план дня; жалоба: нет произвольных диапазонов (3, 5, 7 дней). Идея: переключатель «вчера, сегодня, завтра, дата», позже «несколько дней».
- Odoo Planning и HubSpot: по запросам не нашёл полезных практических отзывов, выводов не делаю.
Отклонено: полноценная панель аналитики и склад остатков (нет данных), экспорт в таблицы (в процессе его нет).

## 4. Две концепции интерфейса

### Концепция 1. «Сводка в шапке» (развитие 4.7)
Кнопка «Выплата … ₽» в шапке. Окно 360 px: вверху переключатель даты, ниже две карточки («Выплата», «Оборудование на завтра»), внизу вкладки «Состав», «Настройки».
- Удобство: быстро, не закрывает календарь, привычно после 4.7.
- Минус: таблица оборудования и раскрытие источников в узком окне тесны, длинные списки прокручиваются.
- Сложность: низкая. Совместимость: уже проверена вживую.

### Концепция 2. «Сводка + рабочий экран» (рекомендую)
Окно в шапке остаётся сводкой (сумма, оборудование на завтра в числах, число замечаний). Кнопка «Открыть рабочий экран» открывает широкое окно (до 960×640, закрывается по Esc) поверх календаря с левой навигацией: «Смена» (выплата и состав), «Оборудование» (таблица по залам и общая, раскрытие броней, поиск и фильтр), «Контроль» (замечания по данным), «Настройки».
- Удобство: на повседневной сводке всё видно за один клик, детали и проверка итога в просторном экране.
- Минус: больше кода и состояний, надо тестировать два размера.
- Совместимость: то же окно поверх страницы, ничего не вставляется в вёрстку Bitrix.

Не берём: боковую закреплённую панель со сдвигом страницы (ломает вёрстку Bitrix), вставку в правую колонку календаря (React-приложение, перерисовка стирает блок, места 200 px).

## 5. Архитектура автоматического расчёта

Слои (всё в одном файле, без сборщика):
1. Данные `crmDay(dateISO)`: `crm.deal.list` по `UF_CRM_DATETIME_START` в границах суток по Москве (начало `00:00+03:00`, конец следующего дня), страницы по 50; `crm.deal.productrows.get` через `callBatch`. Только чтение. Нормализация в записи `{id, hall, start, end, stage, items}` (тот же формат, что у сборщика календаря).
2. Расчёты: существующие чистые функции без изменений (`buildDayList`, `analyzeTomorrow`, `computePayout`). Новое: сводка по позициям с источниками (список броней по ключу позиции).
3. Интерфейс: окно, экран, состояния.

Завтрашняя дата: берётся по Москве (существующая `moscowDate`), не по часовому поясу компьютера. Исключаем стадии семантики F, показываем счётчик исключённых. Время обновления показывается всегда; результат старше 5 минут помечается «устарело». Обновление: при открытии окна, раз в 2 минуты пока окно открыто, и по кнопке. Изменения: сравнение по `DATE_MODIFY` и составу, пометка «изменилось с прошлого расчёта». Ошибка REST: понятное сообщение, прежний способ (данные календаря и вставка списка) остаётся запасным.
Защита от дубля: ключ записи — id сделки; одна сделка = одна запись. Строки с одинаковым названием внутри сделки суммируются, как в существующем `buildDayList`.

## 6. Что нужно подтвердить у Ильи до реализации

1. Концепция: 1 или 2.
2. Общий итог оборудования за день: по залам оборудование не складывается между последовательными бронями (максимум), а между разными залами одного дня считаем суммой (одна единица не может быть в двух залах одновременно)?
3. Филиал: брать автоматически по выбранному в календаре или показывать оба?
4. Права: этим скриптом пользуются только администраторы с доступом к сделкам?

## 7. План реализации (P0, P1, P2)

P0: слой данных REST с тестами на фикстурах, сверка с календарём на сегодня (сравнить `buildDayList` из REST и из DOM), переключатель даты, оборудование на завтра, состояния загрузки и ошибок, откат на прежний способ.
P1: рабочий экран (концепция 2), раскрытие источников, автообновление, «изменилось с прошлого расчёта», контроль данных.
P2: фильтры и поиск, несколько дней, загрузка залов, экспорт.
